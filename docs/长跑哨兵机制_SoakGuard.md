# 长跑哨兵机制（SoakGuard）

> 背景：第二期 G8 24h 实跑曾出现"跑完 24 小时回头看报告才发现 FAIL"——harness 的 token 过期、
> RSS 测量错误、服务是否卡死，全程无人知晓，24 小时白跑。本机制把**事后看报告**改成**过程即发现**。

## 一、是什么

`tests/performance/soak_guard.py` 提供与采样解耦的**独立心跳哨兵线程** + 不变量判定 + 即停告警 + 状态外置。

```
                    ┌──────────────── 主循环（采样，间隔分钟级）──────────────┐
                    │  落增量报告 → 分片睡眠 5s → 检查 should_abort → 收尾    │
                    └───────────────────────────────────────────────────────┘
                                        ▲ 读取 abort_reason
┌────────────── SoakGuard 心跳线程（间隔秒级，默认 30s）──────────────┐
│  alive? → probe? → 硬指标判定 → 软指标计数 → 写状态文件 → 告警即停   │
└────────────────────────────────────────────────────────────────────┘
```

## 二、四条防线

| 防线 | 手段 | 解决的问题 |
|------|------|-----------|
| **主动发现** | 心跳线程按秒级间隔探测，与分钟级采样解耦 | 故障发现延迟从 ≤采样间隔 降到 ≤心跳间隔 |
| **不变量即判** | 进程存活 / HTTP 可达 / 检测计数增长 / RSS 上下限 / P95 上限 | 服务卡死、摄像头掉线、内存泄漏，落地即判 |
| **即停即报** | 判定失败立刻置 `abort_reason`，主循环 5s 内响应并收尾；webhook 告警 | 不再空跑到 duration 结束 |
| **状态外置** | 每心跳原子写 `--status-file`（tmp+replace），随时可查 | 无需翻日志，人/其他会话秒级看健康度 |

**跨会话巡检（第五道防线）**：哨兵解决"进程内即停"，但会话不在时仍无人知晓。配合
**每小时定时自动化**读取状态文件即可覆盖：健康时只输出一行进度，即停/跑完/进程消失
时立即报告并给出原因推断，跑完后自动删除自身。这样 24h 长跑在任意时刻出问题，
**最长 1 小时内必被主动上报**，而不是等跑完回头看。

## 三、判定矩阵

| 指标 | 类型 | 判据 | 默认阈值 |
|------|------|------|---------|
| 服务进程存活 | **硬失败** | `proc.poll() is not None` 一次即停 | — |
| RSS 绝对上限 | **硬失败** | 单次超过 `--max-rss-mb` | 1500 MB |
| RSS 相对增长 | **硬失败** | 超过基线 `--max-rss-growth-pct` | 25 % |
| 检测计数停滞 | 软失败 | 连续 `--max-stall` 次不增长（引擎卡死/掉线） | 3 次 |
| HTTP 不可达 **且流水线停滞** | 软失败 | 连续 `--max-failures` 次判**死** | 3 次 |
| HTTP 不可达 **但流水线仍在推进** | 软失败 | 判"**忙**"（事件循环阻塞/过载），宽限 `--max-busy` 次后才判失败 | 10 次（≈5 分钟） |
| P95 超阈值 | 软失败 | 连续超 `--max-p95-ms` | 3000 ms，3 次 |
| 心跳间隔异常 | 观察 | 记录 `probe_gap_suspected_host_stall`（主机休眠/系统停顿） | 间隔 >2×+10s |

**"忙"与"死"必须分开**：第二信号（DB/WAL 仍在被写入）表明流水线还活着，此时 HTTP 失联
多半是事件循环被周期性任务（清理、备份）阻塞，属于可恢复的忙——只告警并给更长的宽限，
不要几十秒就判死误杀长跑；只有持续失联到 `--max-busy` 才判失败（API 长时间不可用同样是故障）。

硬失败立即即停；软失败需连续 N 次，避免网络抖动误杀。多故障并发时**保留首因**，现场不被覆盖。

## 四、用法

```bash
# 24h 实跑（推荐参数：心跳 30s、状态文件外置、告警 webhook）
python tests/performance/real_camera_soak.py \
  --duration 86400 --sample-interval 300 --cameras cam_net_192_168_1_4,cam_001 \
  --heartbeat 30 \
  --status-file docs/stability/soak_status.json \
  --max-rss-mb 1500 --max-rss-growth-pct 25 --max-p95-ms 3000 \
  --max-stall 3 --max-failures 3 \
  --alert-webhook https://your-webhook-url
```

运行中随时查看健康度（无需等跑完、无需翻日志）：

```bash
cat docs/stability/soak_status.json      # aborted / abort_reason / probes / last_count
tail -f /tmp/soak_24h.log                # [WARN] / [ALERT] 实时事件流
```

即停后报告会带 `aborted: true` 与 `abort_reason`，且 `pass` 一律判 false——**被哨兵叫停的运行绝不可能是"通过"**。

## 五、自检（秒级，不必跑几小时）

```bash
pytest tests/performance/test_soak_guard.py -q   # 8 项：8 passed in ~23s
```

覆盖：健康不误杀、进程退出即停、计数停滞即停、RSS 越限即停、瞬时抖动不误杀、连续软失败即停、状态文件可解析、首因保留。

## 六、踩过的坑（勿重犯）

1. **停滞判据的自我比较**：先 `self.last_count = count` 再比较 `count <= last_count` 恒为真 → 健康运行被误判停滞（假阳性）。必须**先取旧值再更新**。
2. **token 过期**：任何长于 `token_expire_minutes`（默认 720min）的长跑，探测必须自动重登，否则后半程全是 401 伪故障。
3. **RSS 只测单进程**：服务用子进程/多进程时只测主 PID 会得到荒谬小值（实测 3.5MB vs 真实 ~450MB）。必须测进程树求和并启动时打印校验。
4. **采样间隔即发现延迟**：5 分钟采样 = 最长 5 分钟才发现故障。心跳与采样必须分离。
5. **服务端日志丢弃到 DEVNULL**：进程崩溃无栈可查，事后只能猜。必须落盘（`server_<ts>.log`）。
6. **只看 HTTP 判生死**：事件循环被阻塞时 HTTP 会失联，但流水线仍在写库——必须引入
   第二存活信号（DB/WAL mtime）区分"忙"与"死"，否则会误杀可恢复的长跑（实测踩到）。
7. **周期性重活放在事件循环上**：`db.cleanup_retention` + 遍历上万图片文件的清理、
   sqlite 整库备份，曾把 uvicorn 事件循环卡住数十秒（17:31 清理 → 17:37 出现 HTTP 失联采样）。
   一律 `await asyncio.to_thread(...)` 承载。
