### 整体架构评价

后端采用清晰的分层装配模式：`main.py` 只做依赖注入与生命周期管理，业务分散在 `src/` 各单一职责模块（引擎编排 / 检测器 / 帧总线 / 数据层 / 路由层）。多摄并发（任务字典 + 共享检测器推理锁）、共享帧总线（引用计数 + linger 延迟释放 + 断线降级合成帧）、启动治理后台化（避免清理 I/O 卡事件循环）等设计均基于 24h 实跑教训迭代而来，成熟度较高。主要短板在**权限矩阵不一致**（HTTP 与 WS 两套口径）、**告警链路缺少运营级治理**（无冷却/抑制）、以及**配置双数据源**（CameraManager 内存对象与 ConfigManager 配置文件并行赋值）。

前端为 Vue3 + Vite + Element Plus，API 层（401 刷新队列 + 重放）、WS 层（指数退避 + 页面可见性重连）、路由守卫（RBAC）均已组件化且质量良好，无 console.log/v-html 卫生问题。短板在**大视图文件**（DeviceManagement.vue 566 行、Alerts.vue 505 行）与自研 reactive store（Pinia 已安装未使用）。

## 第二部分：问题清单（按严重程度排序）

### 高风险（6 项）

#### H1 第二期全部成果未提交 —— 一次性丢失风险 ｜维度：工程/流程

- **证据**：`git status`：53 个文件 modified；核心新文件 untracked：`edge/src/audit.py`、`image_store.py`、`roi.py`、`routers/audit.py`、`routers/batches.py`、`routers/media.py` 等，以及 `docs/开发计划_第二期_2026-09-03.md`、`docs/stability/`（24h 压测数据）全部未入库。
- **根因**：缺少"验收通过即提交/打标签"的流程门禁；开发全部堆在工作区。
- **影响**：一次误操作（`git checkout .`）或磁盘故障即丢失整期验收通过的代码；远端 CI 仍在跑旧代码，门禁形同虚设；无法回溯压测基线。
- **严重程度**：**高**（不可逆丢失风险 + 工程流程失效）。

#### H2 RBAC 权限矩阵不一致：viewer 可启停产线检测、增删摄像头 ｜维度：安全

- **证据**：
  - HTTP `POST /api/v1/inspection/start|stop` 仅 `Depends(get_current_user)`（[routers/control.py#L8](../edge/src/routers/control.py#L8)），任何角色可调；
  - `routers/cameras.py#L11` 整个路由仅要求登录：viewer 可添加/删除摄像头、修改凭据、`PUT /{id}/active` 切换主摄；
  - 而同一"启停检测"操作走 WS 却要求 admin（[main.py#L331-L337](../edge/main.py#L331-L337)）。
- **根因**：二期安全收口只覆盖了 WS 控制面与 users/config 路由，HTTP 控制面路由（control/cameras）漏改。
- **影响**：访客账号即可启停产线检测、删除摄像头、篡改 RTSP 地址凭据——产线误操作与越权风险；权限模型自相矛盾导致审计口径混乱。
- **严重程度**：**高**。

#### H3 摄像头凭据泄漏：含密码的 RTSP URL 回传任意登录用户 + 明文落盘 ｜维度：安全

- **证据**：
  - 添加/更新摄像头时将凭据注入 source（`build_authed_source`，[routers/cameras.py#L89-L96](../edge/src/routers/cameras.py#L89-L96)、[L132-L147](../edge/src/routers/cameras.py#L132-L147)），并显式回传：`info.source = cfg.source  # 响应需反映已注入的鉴权信息`；
  - `GET /api/v1/cameras` 的 `CameraInfo.source`（[models.py#L163-L171](../edge/src/models.py#L163-L171)）无任何脱敏——viewer 也能拿到 `rtsp://user:pass@host`；
  - 凭据明文写入 config 文件（config API 已有脱敏，但 cameras API 是独立通道）。
- **根因**：摄像头管理功能先于安全收口开发，"响应需反映已注入的鉴权信息"这一便利性设计未过安全评审。
- **影响**：任何登录用户可导出全部摄像头口令；配置文件备份/泄漏即凭据泄漏。
- **严重程度**：**高**。

#### H4 告警无冷却/抑制机制 —— 持续缺陷即告警风暴 ｜维度：功能/运营

- **证据**：`process_alerts` 由检测循环**每帧**调用（[inspection_engine.py#L296](../edge/src/inspection_engine.py#L296)），每帧命中规则即新建 `alert_events` 记录 + 发邮件/webhook（[notifier.py#L161-L204](../edge/src/notifier.py#L161-L204)）；全库 grep 无 cooldown/静默/去重逻辑（database.py#L844 的去重仅针对查询聚合）。
- **根因**：告警链路按"事件流"设计，未考虑同一规则对持续状态的单帧重复触发。
- **影响**：一块持续缺陷布料以默认检测节拍（亚秒级）触发——每小时数千条事件与邮件/webhook，通知渠道被限流封禁、DB 膨胀、关键告警被淹没。质检系统可用性直接受损。
- **严重程度**：**高**。

#### H5 慢通知拖慢检测节拍 —— webhook 超时串在检测工作线程 ｜维度：性能/正确性

- **证据**：`await asyncio.to_thread(process_alerts, ...)` 在检测循环内被 await（[inspection_engine.py#L296-L302](../edge/src/inspection_engine.py#L296-L302)）；`send_webhook` timeout=10s、失败重试 1 次（[notifier.py#L66-L109](../edge/src/notifier.py#L66-L109)）——最坏单帧阻塞该摄检测循环 20s+。模块注释宣称"不影响检测循环节拍"，与实现相悖。
- **根因**：通知发送被放在检测帧处理的事务路径上，而非独立发送队列。
- **影响**：外部 webhook 服务抖动 → 该摄像头漏检、`processing_time_ms` 指标失真；多规则多渠道时放大。
- **严重程度**：**高**（与 H4 同源，一并治理）。

#### H6 24h 压测完整时长未闭环 + 真实 YOLO 权重未替换（上期遗留）｜维度：可靠性/业务

- **证据**：验收纪要 §4/§6：第二轮 24h 实跑进行中（报告未归档）；`detector_mode=yolo` 加载的仍是 COCO 基线权重（[detector.py#L71-L128](../edge/src/detector.py#L71-L128) 诚实标注类别），服装瑕疵模型依赖 1.3 导出样本训练后上传激活。
- **影响**：生产检测精度与"第三期可靠性门禁"均未最终签收。
- **严重程度**：**高**（业务价值兑现的关键路径）。
